# TPC-DS

The [TPC-DS](https://www.tpc.org/tpcds/) decision support benchmark, generated with `dsdgen` from the TPC-DS kit, version 2.10.0. The kit is built from [gregrahn/tpcds-kit](https://github.com/gregrahn/tpcds-kit) at commit `5a3a81796992b725c2a8b216767e142609966752`. Table definitions come from DuckDB's `tpcds` extension.

DuckDB's built-in `dsdgen` reports the same kit version but produces different values, and it cannot generate in chunks. So every scale factor is generated with the reference C kit, which gives the same data whether a table is generated in one go or in children. Empty fields are NULL, as the specification defines.

## Bucket Layout

```text
tpcds/sf<N>/<table>/<table>.{parquet,csv.zip}         # tables that fit in one file
tpcds/sf<N>/<table>/<table>_NNNN.{parquet,csv.zip}    # larger tables
tpcds/sf<N>/<table>/_manifest.json                    # parts written, for resuming
tpcds/sf<N>/queries/qNN.sql
tpcds/sf<N>/schema/<table>.sql, keys.sql
```

Published scale factors: SF1 and SF1000.

Parquet files are about `--target-mb` (default 500 MB). The fact tables are sorted by their date key: `ss_sold_date_sk`, `sr_returned_date_sk`, `cs_sold_date_sk`, `cr_returned_date_sk`, `ws_sold_date_sk`, `wr_returned_date_sk` and `inv_date_sk`. Their parts cover consecutive date ranges, and rows without a date come last. Dimension tables keep generation order.

## Generating

```bash
uv run generate.py tpcds --sf 1
uv run generate.py tpcds --sf 1000 --children 100 --jobs 8
```

The first run downloads the kit and builds `dsdgen` into `temp/tpcds/kit/`, which needs `make` and a C compiler. The Docker image builds it in a separate stage and sets `TPCDS_KIT_DIR` to the result.

- **Dimensions** are each generated by one `dsdgen` call and exported directly.
- **Fact tables** are generated per family: `store_sales` with `store_returns`, `catalog_sales` with `catalog_returns`, `web_sales` with `web_returns`, and `inventory`.
  - With `--children 1`, a family is generated in one go and sorted in DuckDB.
  - With `--children N`, `dsdgen -PARALLEL N -CHILD k` generates slice k. `--jobs` slices run at a time. Each slice is loaded into DuckDB, then staged locally as parquet in `temp/tpcds/sf<N>/staging/`, partitioned by 30-day buckets of the date key.
  - Once every slice is staged, each bucket is sorted and exported, so all children of a family must run on the same machine.

Tested at SF10 with 4 children:
- all fact tables have the row counts from the specification;
- primary keys are unique and parts are in date order;
- `web_sales`/`web_returns` match a single serial `dsdgen` run row for row.

That run took 14 minutes on a laptop with 4 jobs. SF1000 is 100 times the data: give it 64 GB RAM, about 1.2 TB of disk for the staged facts plus the slices being generated, and as many `--jobs` as cores.

## Restarting

Rerun the same command on the same machine. Complete tables and exported buckets are skipped (`_manifest.json`), and staged slices are kept in `temp/` until their table is exported. When a table completes, files in its folder that are not in its manifest, e.g. from an earlier layout, are deleted.

## Queries

`tpcds/sf<N>/queries/q01.sql` to `q99.sql`: the 99 TPC-DS queries from DuckDB's `tpcds_queries()` (DuckDB 1.5.6). They are the same at every scale factor except Q9. Its five thresholds are drawn from 1 to `rowcount("store_sales") / 5` in the kit's template, so they are multiplied by the scale factor to keep each `CASE` branch as selective as at SF1. The other templates that use `rowcount()` only pick ids and counts that stay valid at larger scale factors. Tables are qualified with the namespace, e.g. `tpcds_sf1000.store_sales`. Extracted once and committed:

```bash
uv run generate.py tpcds --sf 1000 --extract-queries
```

## Schema

The DDL is checked in at `tpcds/sf<N>/schema/` (one `<table>.sql` per table, plus `keys.sql` where keys apply) and uploaded unchanged with each run.
