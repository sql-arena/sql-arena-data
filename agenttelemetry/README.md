# Agent Telemetry

Synthetic traces of LLM agents, as observability tools such as Langfuse, Arize Phoenix and LangSmith store them:
one row per span of an agent run (the run itself, each model call, each tool call), with prompts and results as
JSON text, token counts, cost and latency, plus evaluation scores that arrive after the run. The span columns follow
the [OpenTelemetry GenAI semantic conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/).

The data covers one year, 2025, and is built so that time filters do real work, unlike
[AgentLogsBench](../CANDIDATE_DATASETS.md#agent-observability), whose date range covers all of its data:

- Every table is stored sorted by its time column, so a time range skips files and row groups.
- Traffic triples over the year and halves at weekends, so the last 7 days hold about 3% of the spans and a quarter
  about 30%.
- What the data holds changes with the date: models are released and retired, prices change, tenants sign up,
  a release ships every two weeks, and there are outages and a regression on known dates. A query over the wrong
  window gives a visibly different answer.

Generated by `agenttelemetry/agenttelemetry.py`.

## Licence

Synthetic data, generated by this repo. Tenants, users, models (`acme-*`, `globex-*`, `initech-*`), prices and
all text are made up.

## Tables

Namespace `agenttelemetry_sf<N>`. Times are `TIMESTAMPTZ` in UTC, with microseconds.

| Table | Rows at SF1 | Sorted by | What it is |
|---|---|---|---|
| `spans` | 992,000 | `start_time` | One row per span: agent run, model call (`llm`), tool call (`tool`, `retrieval`) |
| `traces` | 99,000 | `start_time` | One row per agent run: its root span with totals of its spans |
| `scores` | 70,000 | `created_at` | Evaluations of runs: LLM judge, user thumbs and human annotation |
| `tenants` | 200 | `tenant_id` | Customers: tier, region, sign-up time |
| `model_prices` | 10 | `model`, `valid_from` | Price per million tokens of each model from a date, and its context size |

Keys are in `agenttelemetry/sf<N>/schema/keys.sql`. A span is identified by `(trace_id, span_id)`, and
`(trace_id, parent_span_id)` points to its parent.

### spans

- **Identity:** `trace_id` (32 hex), `span_id` (16 hex), `parent_span_id` (NULL for the run), `session_id`,
  `tenant_id`, `user_id`.
- **What ran:** `kind` (`agent`, `llm`, `tool`, `retrieval`), `span_name` (`invoke_agent coding-agent`,
  `chat acme-large-2`, `execute_tool bash`), `agent_name`, `tool_name` and `tool_call_id` for tool calls, and
  `provider` and `model` for model calls.
- **Deployment:** `environment` (`prod`, `staging`, `dev`) and `app_release` (`v2.24.0`).
- **Time:** `start_time`, `end_time`, `duration_ms`, and `first_token_time` for successful model calls.
- **Outcome:** `status` (`OK`, `ERROR`), `error_type`, and `finish_reason` (`stop`, `tool_calls`, `error`).
- **Model call figures:** `input_tokens`, `output_tokens`, `cache_read_tokens`, `reasoning_tokens`, `cost_usd`,
  `prompt_name` and `prompt_version`.
- **`attributes`:** a JSON object of OpenTelemetry attributes, such as `deployment.region`, `customer.tier`,
  `app.release`, `gen_ai.request.temperature`, `gen_ai.response.id` and `gen_ai.tool.call.id`. Some keys appear
  only on some runs: `feature.flags` on 20%, and `experiment.id` on 10% from September.
- **`input_text` and `output_text`:** JSON text.
  - A model call's input holds the messages new to that call: the system prompt and the user's task on the first
    call, then the results of the tools the previous call asked for. Its output is the assistant message, whose
    `tool_calls` list the tools to run, with their arguments as a JSON string.
  - A tool call's input is its arguments and its output is the result: file contents, command output, search
    results, SQL rows.
  - Each tool result appears twice, as the tool span's output and in the next model call's input, as in real traces.

### traces, scores, tenants, model_prices

- `traces` repeats the run's identity, deployment, time and outcome. It adds the run's `provider` and `model`, and
  totals of its spans: `span_count`, `llm_calls`, `tool_calls`, `tool_errors`, the four token counts and
  `cost_usd`.
- `scores` has `score_id`, `trace_id`, `span_id` (the run's span), `session_id`, `tenant_id`, `name`, `source`,
  `value`, `label`, `comment` and `created_at`:
  - `helpfulness` from an `llm_judge`, a value from 0 to 1, for 60% of runs, 1 to 6 hours after the run.
  - `user_feedback` from a `human`, `thumbs_up` (1) or `thumbs_down` (0), for 8% of runs, within 30 minutes.
    Some thumbs down have a comment.
  - `correctness` from an `annotation`, `correct` (1), `partially_correct` (0.5) or `incorrect` (0), for 3% of
    runs, 1 to 10 days after the run. Annotations of December runs arrive in January 2026.
  - All three follow a hidden quality of the run, which is higher for larger models and lower for failed runs, so
    the judge and the annotators mostly agree.
- `tenants` has `tenant_id`, `name` (`org_001`), `tier` (`enterprise`, `team`, `free`), `region` and `created_at`.
- `model_prices` has `provider`, `model`, `valid_from`, `input_price`, `output_price`, `cache_read_price` (USD per
  million tokens) and `context_tokens`.

## How the Data Is Made

The generator is DuckDB SQL in `agenttelemetry/sql/`. Every random draw is the `md5` of a salt and the row's key, so
every run gives the same data.

- **Sessions.** On day d there are SF x 180 x (0.5 + d / 364) sessions, x 0.45 at weekends, which is about 55,800
  sessions and 99,000 runs a year at SF1. Start times follow a daily curve, busiest from 10:00 to 18:00 UTC.
  Session n of a day is the same at every scale factor, except for its user, since a larger scale factor only adds
  sessions.
- **Tenants.** 200 tenants have Zipf-distributed traffic, and tenant 1 has 21% of it. Tenants 1 to 20 exist all year
  except tenant 3, which signs up on 2025-07-21; tenant 7, which signs up on 2025-10-06; and the rest sign up during
  the year. Each tenant has SF x 20,000 x its share of users and a main agent.
- **Agents.** Five agents, each with its own tools. 70% of a tenant's sessions use its main agent, so the shares
  of sessions at SF1 follow the large tenants:
  - `support-agent` (32% of sessions): `search_kb`, `get_ticket`, `update_ticket`, `lookup_order`, `send_email`
  - `coding-agent` (23%): `read_file`, `edit_file`, `bash`, `grep`, `glob`, `web_fetch`
  - `research-agent` (18%): `web_search`, `web_fetch`, `read_pdf`
  - `sre-agent` (14%): `query_logs`, `get_metrics`, `kubectl`, `bash`, `page_oncall`
  - `data-agent` (13%): `list_tables`, `describe_table`, `sql_query`, `run_python`
- **Runs.** A session has 1 to 8 runs about 7 minutes apart, all with the session's model.
  - A run is a loop of turns: a model call, then the 1 to 3 tools it asked for, one after another.
  - Each model call is sent the whole conversation so far, so `input_tokens` grows with each turn, and providers
    other than initech serve the previous turns from cache.
  - 35% of coding runs and 30% of research runs call a `task` tool, which runs an `explorer` sub-agent on the
    provider's small model, two levels below the run (`run > task > explorer > its calls`).
  - Tool calls fail at a rate set per tool and the run carries on. A failed model call ends the run.
- **Models.** Seven models in three providers, chosen by weight among those available that day. A new model takes
  six weeks to reach its full share:

  | Model | Available | Price changes |
  |---|---|---|
  | `acme-large-1` | until 2025-06-30 | |
  | `acme-large-2` | from 2025-05-15 | 2025-11-01, about 17% cheaper |
  | `acme-small-1` | all year | |
  | `globex-pro` | all year | 2025-08-01, half price |
  | `globex-flash` | from 2025-03-01, 24,000 token context | |
  | `globex-pro-2` | from 2025-10-20, reasoning | |
  | `initech-reasoner` | from 2025-02-10, reasoning, no cache | 2025-07-01, 45% cheaper |

  `cost_usd` is computed from the price in force at the call's `start_time`. Failed calls cost 0. Long coding runs
  on `globex-flash` fail with `context_length_exceeded`.

### Events on Known Dates

| When (UTC) | What | Seen in |
|---|---|---|
| 2025-03-18 13:00 to 16:30 | globex model calls fail with `overloaded_error` 35% of the time | Q18 |
| 2025-07-09, all day | `web_search` is 6x slower and times out 40% of the time | Q28 |
| 2025-09-02 14:00 to 15:15 | acme model calls fail with `rate_limit_error` 50% of the time | Q19 |
| release `v2.24.0`: staging 2025-11-12 to 11-25, prod 2025-11-19 to 12-02 | `edit_file` fails with `patch_failed` 30% more often | Q21 |
| 2025-11-28 (Black Friday) | 1.5 times the day's sessions on top, all support: 450 support sessions at SF1, against 68 the Friday before | |
| from 2025-09-01 | `experiment.id = ctx-compression-b` on 10% of sessions | |

### Needles

The planted text is the same at every scale factor, because it is placed on the first matching run of a day:

| Text | Where | Rows |
|---|---|---|
| `export PAYMENTS_API_KEY=sk_live_…` (a fake Stripe key) | one `bash` result on 2025-06-12, and the model call that reads it | 2 (Q10) |
| `ERR_LEDGER_SHARD_7731` | one `query_logs` result on each day from 2025-10-06 to 10-12, and the model calls that read them | 14 in 7 runs (Q11) |
| `Ærøskøbing` | one support task on 2025-02-03: the run's input and its first model call | 2 (Q13) |

Q01 and Q02 look up a run (`921e2a502330c3c5a575a230009d95c1`) and its session on 2025-10-28, which also exist at
every scale factor.

## Queries

`agenttelemetry/sf<N>/queries/q01.sql` to `q28.sql` follow the query shapes of the observability tools: trace and
session lookups, dashboards, trace lists, text search, JSON attributes, span trees, errors, evaluations and cost.
"Now" is the end of the year, so "last 7 days" is `start_time >= '2025-12-25'`.

Every query but Q10 (search the whole year for a leaked key) and Q26 (the model mix of each week) filters on time.
These are the shares of `spans` in their windows at SF1:

| Window | Queries | Share of spans |
|---|---|---|
| 1 hour | Q16 | 0.05% |
| 1 day | Q01, Q03, Q06, Q14 (and Q02's 3 days of `traces`) | 0.3 to 0.5% |
| 3 days | Q28 | 1.0% |
| 7 days | Q05, Q09, Q11, Q15, Q17, Q24 | 2.4 to 2.9% |
| 14 days | Q25 | 3.8% |
| a month or 30 days | Q04, Q07, Q12, Q13, Q18, Q21, Q22, Q27 | 4.7 to 12% |
| a quarter | Q08, Q20, Q23 | 28 to 35% |
| all | Q10, Q26 | 100% |

| Query | Shape |
|---|---|
| Q01 | All spans of one run, bounded by its day as Langfuse does |
| Q02 | The runs of one session |
| Q03 | Hourly p50/p95 model latency by model, last 24 hours |
| Q04 | Daily cost and tokens by tier and model, last 30 days, joined to `tenants` |
| Q05 | Time to first token and output speed by model, last 7 days |
| Q06 | Trace list: page 2 of one tenant's slowest runs of a day, with scores |
| Q07, Q08 | Top 20 users by cost in November; the 100 most expensive runs of Q3 |
| Q09 | Tool facet: calls, error rate and p95 latency per tool |
| Q10, Q11, Q13 | Needles: a key over the whole year, an error code in one week, a non-ASCII name in February |
| Q12 | `ILIKE` phrase in tool results by tool, last 30 days |
| Q14, Q21 | Group by JSON attributes: region and tier for one day; release, to find the regression |
| Q15 | Unnest the tool calls in the model output JSON and join them to the tool spans by `tool_call_id` |
| Q16 | Recursive CTE over the span tree of one hour's runs |
| Q17 | Self-join of sub-agent runs to their model calls |
| Q18, Q19 | Model call error rate by provider and day in March; 5-minute error buckets on 2025-09-02 |
| Q20 | First error of each failed run, with `arg_min` |
| Q22, Q23 | Judge score by model; judge against annotators, with scores filtered on `created_at` |
| Q24 | Sessions: runs per session, user think time with `lag`, context growth |
| Q25 | Cost recomputed with an `ASOF JOIN` to `model_prices` across a price change; equals `cost_usd` |
| Q26 | Weekly model mix over the whole year, which shows the rollouts |
| Q27 | December spend of the tenants that signed up in the second half of the year |
| Q28 | `web_search` latency and timeouts by hour around the 2025-07-09 outage |

The queries use DuckDB function names (`quantile_cont`, `arg_min`, `json_extract_string`, `time_bucket`,
`ASOF JOIN`), as the other query sets do. They were written for this dataset and checked against SF1.

## Bucket Layout and Generating

```text
agenttelemetry/sf<N>/<table>/<table>[_NNNN].{parquet,csv.zip}
agenttelemetry/sf1000/<table>/<table>_<DDD>_<NN>.parquet     part NN of the chunk starting on day DDD of the year
agenttelemetry/sf<N>/queries/, agenttelemetry/sf<N>/schema/
```

SF1 and SF10 have parquet and csv.zip. SF1000 is parquet only: 986 million spans, about 760 GB of parquet.

```bash
uv run generate.py agenttelemetry --sf 1                         # 992,000 spans, 750 MB of span parquet
uv run generate.py agenttelemetry --sf 1 --days 14 --no-upload   # a quick test
# SF1000 in 6 shards, run at the same time (3 on each of two machines), then combined
uv run generate.py agenttelemetry --sf 1000 --parquet-only --shard 0/6    # ... to --shard 5/6
uv run generate.py agenttelemetry --sf 1000 --parquet-only --merge-shards 6
```

The fact tables are generated in chunks of consecutive days, about one 500 MB spans file each, and resumed per chunk
through `_manifest.json`. At SF1000 a chunk is one day of several files. On a laptop SF1 takes about 2 CPU minutes
and SF10 about 35, plus the upload. Size grows linearly with SF.

`--shard K/N` generates every N-th chunk from chunk K and resumes through its own `_manifest_K_of_N.json`. The data
is the same as unsharded, as every day is generated from its own seeds. Shard 0 also writes the dimensions and the
queries and schema. Once all shards are complete, `--merge-shards N` combines their manifests into `_manifest.json`.
